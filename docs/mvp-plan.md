# MVP 执行计划（草稿）

最后更新：2026-10-21。这是讨论稿，标「待定」的地方要我们拍板，或者等馆方确认（汇总在第 9 节）。

## 1. 目标和范围

**目标**：BENCHMARK 三家店的日常运营从青橙换到我们的系统：卖卡、入场、会员管理、看数据。三家店的次卡通用，所以不按店试点，三家店一起切；切换前先影子运行两周（做法见 5.6）。

**MVP 要做的**

| 端 | 功能 |
|---|---|
| 小程序 | 微信登录 + 手机号验证（用来认领从青橙导入的老卡）；首页；购卡（期限卡、次卡、单次票）+ 微信支付；卡包和使用记录；扫码入场（第一次签风险告知书，入场记录标记当日保险）；次卡转赠和领取；老带新；我的（攀爬日历、订单记录、保险与告知书） |
| 后台 | 数据看板（营收、入场、新客来源、老带新转化、7 天内到期）；会员（搜索、详情、卡、流水）；前台操作（线下收款开卡、手动登记入场、撤销入场、调整次数和有效期、退款）；卡种与价格；入场记录和分享记录；员工账号和权限；导出 Excel；青橙数据导入和对账 |
| 前台设备 | 一个网页，在前台平板上显示动态入场码和实时入场列表（入场方式待馆方确认，见 5.3） |

**第一期也要做（2026-10-21 定）**：团课、私教、活动报名、跟保险公司对接自动投保、美团/大众点评接入。所有功能一起上线，不分批。

**放到第二期的**：定线分析（入场记录从第一天就带门店，数据先攒着）；问数据；其他岩馆自助入驻。

后台的前台操作原型里几乎没有，但真用起来每天都离不开：线下收现金开卡、有人手机没电要手动登记、扣错了要撤销、会员要退款。所以这部分要放进 MVP。

## 3. 技术选型（建议，待你拍板）

**后端：Node.js 20 + TypeScript + Fastify + PostgreSQL**，代码放 `services/api`。

- 可以直接复用 `@climb/core` 的规则和 `@climb/api` 的类型，前后端只有一份规则。
- 卡、流水、订单、对账、报表都是关系型数据，用 PostgreSQL 做事务和统计最顺手。
- 查数据库用 Kysely（只写 SQL 的类型层，没有很多魔法）。迁移脚本用纯 SQL 文件，方便看懂、方便审查。
- 一套部署服务所有岩馆，每张表都带 `gym_id`。

**为什么不用微信云开发**：云开发登录鉴权确实方便，但云环境绑在单个小程序上，每家岩馆是一个独立的小程序（营业执照不同），以后做多岩馆平台、让后台网页访问都很别扭；它的文档数据库做对账和报表也比较吃力。

**部署：放在馆方自己的云账号里（已定）**。馆方用营业执照开一个腾讯云或阿里云账号，给你一个有权限的子账号。服务器、数据库、域名、微信支付密钥都在馆方账号里，账单馆方直接付。这样最直接地回应馆长「怕数据丢、怕你不做了」的顾虑：数据和账号一直是他的，换人接手也只是换个子账号。

代码照样按多岩馆写（每张表带 `gym_id`），既能给一家岩馆单独部署，也能以后多家共用一套部署。第二家岩馆来了再决定用哪种；那时要做平台，就用你的公司开服务器，支付走微信支付服务商模式。

分测试和正式两套环境：

- 一台轻量服务器，用 Docker 跑 API 和前台网页。
- 云数据库 PostgreSQL：托管服务自带每日自动备份和按时间点恢复，这正好是我们答应馆长的「数据不会丢」。
- 对象存储：放每日备份和导出文件。
- 后台网页是静态文件，放对象存储或者同一台服务器上。
- 量很小，每月费用应该在几百元以内，开通前按官网价格再核一次。

## 4. 数据模型

### 通用约定

- 主键用 UUID v7（按时间递增，方便排序），字段名 `id`。
- 每张业务表都有 `gym_id`。后端从登录身份里取岩馆，不信任前端传来的岩馆 ID，所有查询都按它过滤。
- 金额用「分」存整数，字段以 `_cents` 结尾。
- 业务日期（入场日、到期日）用 `date`，按岩馆时区（`Asia/Shanghai`）算，对应代码里的 `DateKey`；时间点用 `timestamptz`。
- 不物理删除。作废、退款、撤销都用状态字段，并记下谁、什么时候、为什么。
- **卡的次数和有效期每次变化都在 `card_ledger` 里记一笔，只追加不修改**。`cards.remaining` 只是方便查询的缓存，和流水在同一个事务里更新。每天跑一次检查，确认两边一致。出了问题，靠流水能查清每一次是谁改的。

### 表

```sql

-- 员工（后台登录）

members     (id, gym_id,
```

**第二期再加**：`route_sets`（换线登记）、`classes` / `bookings`（团课、私教）、`events`（活动）、`insurance_policies`（跟保险公司对接以后）。

### 几个设计上的考虑

1. **三店通用**：卡不绑门店；入场记录、订单、员工带门店。以后如果某种卡只在一家店能用，再给 `products` 加适用门店。
2. **好友送的次卡**单独算一张卡（`kind = gift`），跟原卡是两行，流水各记各的。原卡记 `share_out -N`，领取人的卡记 `claim +N`，对账时两边能对上。
3. **老会员认领**：导入时按手机号建会员和卡，`openid` 先空着。会员第一次打开小程序时验证手机号，手机号对上了就把 `openid` 补上，原来的卡自动出现在卡包里。所以手机号验证是登录的必经步骤。
4. **身份证号**：MVP 不存。保险如果需要，按馆方定下的方式再加，到时候加密存储，界面上只显示脱敏后的号码。
5. **`@climb/core` 要补的**：卡的状态（冻结、作废）、入场带门店、分享过期退回；类型从后端的表推出来，或者反过来，保持一份。

## 5. 关键流程

### 5.1 登录

小程序调 `wx.login` 拿到 code → 后端用这个岩馆的 AppID 和密钥换 openid → 签发我们自己的 token。第一次登录要求用微信的手机号快速验证（这个按次收费，每次几分钱，量小可以忽略），对上青橙导入的老会员就绑定。

后台员工 MVP 先用手机号 + 密码登录，按角色控制权限：前台只能做前台操作，店长能改价和退款，老板能看所有店的财务。

### 5.2 购卡和支付

**开通要做的事（馆方的账号，你陪着操作）**

1. 小程序完成微信认证（每年 300 元，没认证不能开通支付）和小程序备案。
2. 商户号：馆方自己的普通商户号可以直接用。如果现在是青橙服务商下的特约商户，接口由青橙代为调用，我们拿不到权限，要在小程序后台新申请一个普通商户号（不收开户费，要审核）。
3. 商户平台里把小程序 AppID 关联到商户号，小程序后台确认。
4. 商户平台「账户中心 → API 安全」：申请 API 证书（得到商户私钥）、设置 APIv3 密钥、拿到微信支付公钥和公钥 ID（新商户都用这种方式验签，不再用平台证书）。这几样只放在馆方云账号里的服务器上。

**费用**：没有接口调用费。每笔交易微信收手续费，一般是 0.6%，以商户平台显示的为准。馆方现在用青橙收款应该已经在付这笔手续费了，不算新增成本。

**开发**：大约一周，包括退款和对账。Node 没有微信官方 SDK，用社区的 `wechatpay-axios-plugin` 或自己写签名（RSA-SHA256 签名、回调 AES-256-GCM 解密），代码量不大。

1. 小程序下单 → 后端建 `pending` 订单，存商品快照 → 调微信下单接口拿到支付参数 → 小程序拉起支付。
2. **只有收到并验证过微信的支付回调，才发卡**。回调可能重复到达，用 `out_trade_no` 和「只有 pending 能变成 paid」的条件更新保证只发一次。
3. 回调丢了怎么办：小程序支付完以后主动问一次后端，后端去微信查单补上；再加一个定时任务扫描超过几分钟还是 pending 的订单。
4. 线下收款（现金、POS、转账）：前台在后台开单，`channel` 记成对应方式，直接发卡。财务按渠道分开统计。
5. 下单时设置过期时间（比如 15 分钟），过期没付的订单关单。
6. 每天下载微信的交易账单，跟我们的订单逐笔对一遍。
7. 微信支付 APIv3 没有沙箱，测试就是在真实商户号上付 0.01 元再退款。

**预付卡报送（待确认）**：如果门店在上海，体育健身的预付卡销售要报送给市里的单用途预付卡协同监管服务平台，还有预收资金存管、单人预付金额上限这类要求，细则正在修订。我们的系统替换青橙以后，这部分报送也要接过来。工作量要等拿到对接规范才知道，先问馆方现在是怎么报的。

### 5.3 扫码入场

**建议用前台平板显示的动态码，不用印出来的固定码**。固定码被人拍照发到群里，就能在家「入场」。

1. 前台平板打开前台网页，显示二维码，每 30 秒换一次。码里是门店和一次性 token（后端签发，用过或过期就作废）。二维码配置成「扫普通链接二维码打开小程序」或者直接用小程序码，会员用微信扫一扫就进小程序签到页，不用先打开小程序。
2. 会员扫码进入签到页 → 后端验签、确认码没过期 → 用 `@climb/core` 列出能用的卡 → 会员选卡确认（第一次入场先签告知书）。
3. 后端在一个事务里：锁住这张卡 → 写入场记录 → 扣次、记流水。同一天再次入场 `deducted = 0`，数据库的唯一索引兜底，连点两次也不会扣两次。
4. 平板上的实时列表马上出现这个人（头像、名字、用的什么卡），前台扫一眼就能确认。

入场方式已定（2026-10-21）：会员扫前台平板上的码，见第 9 节。

### 5.4 次卡转赠和老带新

- 发起：后端用 `@climb/core` 校验，原卡扣次、记流水，生成带 `token` 的分享，小程序用 `onShareAppMessage` 把带 token 的页面路径发给微信好友。
- 领取：朋友点开 → 登录 → 后端校验并生成好友送的次卡或体验券。
- 待定：转赠出去一直没人领、到期了，次数退不退回原卡（我建议退，`share_return` 记一笔）；能不能主动撤回还没领的分享。

### 5.5 退款和人工调整

- 退款：店长在后台发起 → 走微信退款（线下收的钱线下退，只记录）→ 卡改成 `refunded`，流水记一笔。用过一部分的次卡怎么折算，按馆方规则来（待定）。
- 调次数、改有效期、撤销入场：必须填原因，写流水和操作日志。

### 5.6 从青橙迁移

1. 拿到青橙的导出文件后，写导入脚本：按手机号建会员，建卡（种类、剩余次数、到期日），`source = legacy_import`，记下青橙的 ID。
2. 导完生成对账表：每个会员在青橙的数字和导入后的数字一行一行对，不一致的标红。
3. **影子运行两周**：青橙照常是正式系统，会员没感觉。我们每天导入一次、对一次账；员工在新后台上练手；小程序只给员工和几位熟悉的会员用，付款用 0.01 元测试。
4. **切换**：挑一个人少的工作日，晚上青橙停止卖卡，做最后一次导入和对账，第二天开放小程序。青橙再保留一个月当只读备份。
5. **回退**：小问题，前台手动登记入场；大问题，把我们的数据按青橙的导入格式导出、导回青橙（前提是青橙支持批量导入）。

## 6. 接口清单（MVP）

在 `@climb/api` 现有约定稿的基础上补全。

**会员端**

| 接口 | 用途 |
|---|---|
| `POST /auth/wx-login` | code 换 token |
| `POST /auth/phone` | 手机号验证，绑定老会员 |

## 8. 上线保障

- **备份**：数据库每天自动备份、可以按时间点恢复；每天再导出一份到对象存储，保留 30 天；每周自动给馆方一份 Excel。上线前至少做一次恢复演练。
- **监控**：接口健康检查；报错、支付回调失败及时发提醒；每天自动对账（流水和余额、我们的订单和微信账单），有差异就提醒。
- **环境**：测试和正式完全分开；小程序体验版连测试环境。
- **安全**：商户密钥和证书只放在服务器上；接口按岩馆隔离；员工按角色分权限；所有改动进操作日志。
- **隐私**：写好隐私政策和个人信息收集说明（手机号、入场记录），小程序后台的隐私保护指引要填。
